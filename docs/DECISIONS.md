| 2026-07 | Modèles attribués **par tâche produit** (registre `LLM_TASKS` dans lib/llm.ts, override env `LLM_TASK_*`) ; observabilité et évals **Langfuse** prévues avant la Phase 2 (traces par tâche, tests A/B de modèles) | Le bon modèle au bon endroit ; coûts et qualité mesurables tâche par tâche |
| 2026-07 | **Nepteo ne détient ni ne déplace jamais de fonds** : pour les campagnes payantes, le budget vit sur le compte publicitaire du client (Meta/Google), avec son propre moyen de paiement. L'agent ne fait que des appels API (budget, statut, ciblage) ; c'est la plateforme qui facture le client. Aucun encaissement, aucun solde, aucun reversement par Nepteo | Éviter le statut d'établissement de paiement (agréments, DSP2, contrôle des fonds). Conséquence : « lancer une campagne / augmenter un budget » = action la plus engageante → validation obligatoire + plafond de budget serveur ; on démarre par « mettre en pause » (ne fait que réduire la dépense) |
| 2026-07 | **Correspondance de colonnes configurable** à la connexion d'un connecteur : au-delà de la détection auto (mots-clés d'en-tête pour Sheets, type + mots-clés de propriété pour Notion), un écran de mapping laissera le client relier ses colonnes aux champs Nepteo (nom, email, entreprise, statut). Non encore construit — backlog Phase 2/onboarding | Les clients arrivent avec leurs propres intitulés ; la détection auto ne couvre pas les cas exotiques (« Structure », « Pipeline »…). Le schéma `prospects` reste **interne et normalisé** (créé une fois par Nepteo, jamais par le client, tout l'original conservé dans `raw`) ; le mapping explicite supprime la rigidité avant l'ouverture multi-clients |

| 2026-07-25 | **Recherche web via Perplexity (Agent API), hors de la couche LLM** : `lib/research/*` appelle `POST /v1/agent` en `fetch` (aucune dépendance npm) pour COLLECTER des faits sourcés ; la couche LLM existante (`LLM_TASKS`) les met en forme. Presets par type de recherche (`low` pour l'identité, `fast` pour une fiche société), surcharge par `PERPLEXITY_PRESET` | Deux rôles distincts : chercher ≠ rédiger. Garder Perplexity hors de `lib/llm.ts` évite de mélanger un fournisseur de recherche facturé à la requête avec le registre de modèles de génération. Sans `PERPLEXITY_API_KEY`, la recherche est simplement désactivée — rien ne casse |
| 2026-07-25 | **L'enrichissement d'un prospect porte sur sa SOCIÉTÉ, jamais sur la personne** : les requêtes interdisent explicitement les informations sur des personnes physiques ; le cache est indexé par société | RGPD : rechercher sur une personne nommée exigerait une base légale documentée, l'information des personnes et un droit d'opposition. Le contexte société (secteur, taille, actualité publique) est ce qui sert réellement à personnaliser une relance, avec une base légale simple. À rouvrir seulement si un pilote le demande, et alors avec le cadre juridique complet |
| 2026-07-25 | **Une recherche web est traitée comme une exécution** : garde-fous serveur (clé > bouton d'arrêt > sujet > plafond `MAX_RESEARCH_PER_DAY`), entrée au journal AVANT l'appel, résultat mis en cache 30 jours par (org, type, sujet) — échecs compris | C'est un appel externe **facturé à la requête**. Même discipline que l'envoi : rien d'irréversible ou de coûteux sans trace préalable et sans plafond non contournable depuis l'UI. Mettre les échecs en cache empêche une clé invalide de boucler et de vider le budget |

| 2026-07-26 | **La recherche web devient multi-fournisseurs : OpenAI `web_search` (Responses API) en plus de Perplexity**, derrière une interface unique (`lib/research/provider.ts`, `RESEARCH_PROVIDER`). Perplexity **n'est pas supprimé** ; le fournisseur effectif est choisi par variable d'env, à défaut par la présence d'une clé. `POST /v1/responses` en `fetch` natif, `tools: [{type:"web_search"}]` + `include: ["web_search_call.action.sources"]` — toujours aucune dépendance npm. Chantier cadré dans `docs/projets/recherche-web-openai.md` | **Contexte** : la clé OpenAI est déjà active, le compte Perplexity API reste à créer — donc la recherche est éteinte en pratique, et avec elle le 2e écran d'onboarding (le premier « waouh » avant tout connecteur). **Décision** : ajouter un fournisseur plutôt qu'en troquer un, pour que le choix reste réversible en une variable d'env. La séparation « la recherche vit hors de `lib/llm.ts` » (25/07) est ce qui rend ce changement peu coûteux : seuls un adaptateur et un parseur bougent. **Conséquences** : (1) une requête OpenAI peut déclencher **plusieurs recherches facturées** en mode agentique — `MAX_RESEARCH_PER_DAY` compte des appels `runResearch`, pas des recherches du fournisseur ; à mesurer et borner (`search_context_size`), sinon le plafond ment ; (2) `researchConfigured()` quitte `perplexity.ts` pour `provider.ts` (4 imports à suivre) ; (3) le 2e écran d'onboarding se rallume dès qu'une clé existe — à retester avant la démo ; (4) `gpt-4o-search-preview` est arrêté depuis le 2026-07-23 et `web_search_preview` est legacy : ne pas les utiliser |
